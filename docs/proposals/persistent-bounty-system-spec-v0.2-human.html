Persistent bounties for deferred scientific work

A bounty would be one durable Git record for a deferred PR: what is blocked, what must change, who may claim it, and when it can return. This gives ScienceAccelBench a safe pause button without confusing unfinished work with an approved task.

1

The one-minute view

The current system handles ideas and active task PRs, but it has no durable home for work that is valuable yet not ready.

!

The problem

Keeping weak task PRs open makes the active queue misleading. Closing them can bury the reason, evidence, and route back to useful work.

B

The proposal

Store each deferred work item as one strict JSON record in Git. Every meaningful change becomes canonical only after a reviewed PR is merged.

✓

The safety model

The ledger records readiness and blockers. It never grants scientific approval, ownership transfer, compute consent, merge authority, or payment.

A bounty is

  • a durable, public work item;
  • a clear statement of what is blocked and what evidence would unblock it;
  • a PR-governed route from “not ready” to completed work;
  • a link between past PR evidence and future packaging work.

A bounty is not

  • money, a compute budget, or leaderboard points;
  • a task submission or accepted module cut;
  • permission to run, push, comment, approve, reopen, merge, or publish;
  • an automatic assignment to whoever comments first.
2

How work would move

Every arrow represents an explicit human-reviewed transition. Time, a comment, a branch, or a bot event never moves a bounty automatically.

Discussion Idea or blocker

An issue or review reveals valuable work that is not ready for delivery.

Merged PR Publish bounty

Scope, blockers, acceptance, ownership mode, and links enter Git main.

Merged PR Accept a claim

A contributor proposes a plan. An open claim PR is not yet a claim.

Normal skill stops Do the work

Source, module, test, run-plan, tolerance, and review gates still apply.

Merged PR Review delivery

The linked source, task, or repair PR is judged on its own evidence.

Merged evidence Complete

Only merged delivery evidence and satisfied acceptance items finish the bounty.

Canonical truth: ScienceAccelBench main. The watcher may report activity, but it never owns or changes bounty state.

4

A lifecycle people can read

The main path is simple. paused and retired remain deliberate curator choices available from the active stages.

needs_scopeKnown work, but not ready to claim
openScope and acceptance are ready
claimedOne claim PR has been merged
in_progressAccepted claimant has begun
in_reviewLinked delivery is under review
completedMerged evidence satisfies acceptance

Who can claim?

By default, only the original source vendor. A broader assignment requires an explicit curator decision recorded through a merged transition PR.

What makes a claim real?

A merged claim PR. “I will take it,” an issue assignment, an open PR, or a branch is only a proposal.

What makes it complete?

Linked delivery PRs are merged and each observable acceptance item has evidence. A green bounty record cannot replace scientific review.

8

What remains human-owned

The ledger improves memory and workflow clarity; it deliberately does not mechanize scientific or project authority.

Software can enforce

  • strict fields, enums, IDs, and safe paths;
  • one record per bounty and no duplicate IDs;
  • state and claimant consistency;
  • deterministic generated-index freshness;
  • the distinct sciaccel-bounty label;
  • no retroactive bounty requirement for existing tasks.

Humans still decide

  • whether scope is ready to open;
  • who may claim and whether ownership changes;
  • whether acceptance is scientifically sufficient;
  • run location, resources, tolerances, and reward policy;
  • whether to comment, close, reopen, approve, merge, pause, or retire.

Ownership modes: original_vendor_only (default), curator_assigned (one explicit named exception), and open_call (anyone may propose; nobody owns it until a claim PR merges). One active claimant maximum.

No clocks: review_after is advisory. Expiration, reassignment, retirement, and reopening always require a merged PR and curator decision.

PR workflow: publish, claim, work, complete

Publish

  1. Discuss the need if necessary; sciaccel-idea remains discussion only.
  2. Add one bounty record and regenerate indices.
  3. Open a PR labelled sciaccel-bounty, never sciaccel-task.
  4. Present state, claimability, note, blockers, required work, acceptance, ownership, and links.
  5. Merge publishes the bounty.

Claim and work

  1. A contributor proposes a narrow record/index change with plan and capacity.
  2. Only a merged claim PR sets claimed and one claimant.
  3. A merged transition records in_progress.
  4. Source/task work continues through the normal package-sciaccel-task human stops.
  5. A linked delivery PR plus merged transition records in_review.

Complete, pause, retire

completed requires merged delivery PRs and evidence for every acceptance item. paused blocks more work but preserves the claimant. retired records why work is no longer wanted; it deletes nothing. Bots close or reopen nothing automatically.

Canonical skill and CLI surface 
sab.py bounty list [--state <state>] [--codebase <slug>]
sab.py bounty show --id <id>
sab.py bounty init --id <id> --codebase <slug> --kind <kind> --out <checkout>
sab.py bounty validate [--id <id>] [--all]
sab.py bounty present --id <id>
  • list, show, validate, and present are read-only.
  • init writes only a local scaffold. It cannot open a PR, claim, transition, run, or merge.
  • brief and status show matching bounties and visible human STOPs.
  • No command converts private --human-ref text directly into public bounty state.
  • The briefing distinguishes an issue (discussion), bounty PR (publishes work), and task PR (delivers work).
Implementation acceptance tests
  1. Schema accepts the three intended records and rejects unknown fields, duplicate IDs, invalid states, bad paths, and contradictory claim fields.
  2. Generation is deterministic; validation fails stale index.json or index.md.
  3. bounties/** receives sciaccel-bounty, never sciaccel-task.
  4. sab.py bounty list/show/validate/present is stable; init creates only a local scaffold.
  5. brief explains issue vs bounty PR vs task PR and each human stop.
  6. status renders state, claimability, note, and blockers accurately.
  7. Existing codebases and tasks without bounty records behave exactly as before.
  8. Validation and tests require no network.
  9. Vendored skill bytes and manifests match the canonical pipeline commit.
  10. Existing source, report, task, PR, branch, and Git history remain present and are not silently rewritten.
Explicit non-goals
  • No automatic contributor assignment, expiration, closure, reopening, merge, or comment.
  • No money, payment ledger, compute promise, reward weights, or leaderboard points.
  • No replacement for the task registry, source reports, issues, PRs, or packaging pipeline.
  • No scientific tolerance or reward decision.
  • No deletion, source removal, history rewrite, or retroactive ownership grant.
  • No watcher-owned state; Git main remains canonical.
